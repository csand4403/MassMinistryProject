# 009_multi_day_templates.sql

The file had pre-existing uncommitted local modifications at the start of the session. I kept and committed the working copy because live Supabase confirms `mass_template.day_of_week` is running as array data for non-null weekday templates, including consolidated multi-day templates.

Diff vs committed version, summarized:

```diff
-- Old committed order:
ALTER TABLE mass_template
  ALTER COLUMN day_of_week TYPE integer[]
  USING CASE WHEN day_of_week IS NULL THEN NULL ELSE ARRAY[day_of_week::integer] END;

DO $$ BEGIN
  ALTER TABLE mass_template DROP CONSTRAINT IF EXISTS mass_template_day_of_week_check;
EXCEPTION WHEN undefined_object THEN NULL; END $$;

-- Working copy order:
DO $$ BEGIN
  ALTER TABLE mass_template DROP CONSTRAINT IF EXISTS mass_template_day_of_week_check;
EXCEPTION WHEN undefined_object THEN NULL; END $$;

ALTER TABLE mass_template
  ALTER COLUMN day_of_week TYPE integer[]
  USING CASE WHEN day_of_week IS NULL THEN NULL ELSE ARRAY[day_of_week] END;
```

There are also small comment and alignment cleanups later in that migration. The meaningful behavioral change is dropping the old integer check constraint before altering the column type, because Postgres can otherwise evaluate the integer check against `integer[]` during the type change.

Live Supabase check:

- Saturday templates return `day_of_week` as `[6]`.
- `Weekday 8:15 AM (Mon/Wed/Fri)` returns `[1,3,5]`.
- `Weekday 5:30 PM (Mon-Fri)` returns `[1,2,3,4,5]`.
- `Weekday 8:00 AM (Tue/Thu)` returns `[2,4]`.

Decision: committed the working copy cleanly rather than reverting.
